# ✅ Рефакторинг JWT Security — Переход на Stateless-архитектуру

## 🎯 Цель

Устранить **N+1 проблему** в security layer, где каждый HTTP-запрос вызывал `UserDetailsService.loadUserByUsername()`, что приводило к запросу в БД на каждый endpoint.

## ✨ Что изменилось

### 1. **JwtService.java**

#### 📥 Добавлены импорты:
```java
import org.springframework.security.core.GrantedAuthority;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import java.util.Collection;
import java.util.List;
import java.util.stream.Collectors;
```

#### 🔧 Изменения в методах:

**a) `generateToken(UserDetails userDetails)`**
- Теперь **извлекает роли/authorities** из `UserDetails`
- **Внедряет их в JWT claims** под ключом `"authorities"`
- Это позволяет избежать повторных DB-запросов при валидации токена

```java
public String generateToken(UserDetails userDetails) {
    var authorities = userDetails.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority)
            .collect(Collectors.toList());

    Map<String, Object> claims = new HashMap<>();
    claims.put("authorities", authorities);

    return generateToken(claims, userDetails.getUsername());
}
```

**b) Новый метод `extractAuthorities(String token)`**
- **Парсит роли обратно из JWT** (без обращения к БД)
- Возвращает `Collection<? extends GrantedAuthority>`
- Используется в фильтре для заполнения `SecurityContext`

```java
@SuppressWarnings("unchecked")
public Collection<? extends GrantedAuthority> extractAuthorities(String token) {
    var claims = extractAllClaims(token);
    var authoritiesList = (List<String>) claims.get("authorities");

    if (authoritiesList == null || authoritiesList.isEmpty()) {
        return List.of();
    }

    return authoritiesList.stream()
            .map(SimpleGrantedAuthority::new)
            .collect(Collectors.toList());
}
```

**c) Новый метод `isTokenValid(String token)`**
- **Stateless-версия** валидации (проверяет только подпись и срок действия)
- **НЕ требует `UserDetails`**
- Старый метод `isTokenValid(token, userDetails)` сохранён для обратной совместимости

### 2. **JwtAuthenticationFilter.java**

#### ❌ Удалено:
- Зависимость от `UserDetailsService`
- Вызов `userDetailsService.loadUserByUsername(username)` — **источник N+1 проблемы**

#### ✅ Добавлено:
- Аннотация `@RequiredArgsConstructor` (Lombok) для DI
- Javadoc с пометкой "Stateless JWT Authentication Filter"

#### 🔄 Рефакторинг `doFilterInternal()`:

**Старый подход (с БД-запросом):**
```java
UserDetails userDetails = userDetailsService.loadUserByUsername(username); // 💥 DB call!
if (jwtService.isTokenValid(jwt, userDetails)) {
    var authToken = new UsernamePasswordAuthenticationToken(
        userDetails, null, userDetails.getAuthorities()
    );
    // ...
}
```

**Новый подход (stateless):**
```java
if (jwtService.isTokenValid(jwt)) { // ✅ No DB call
    var username = jwtService.extractUsername(jwt);
    var authorities = jwtService.extractAuthorities(jwt); // ✅ From JWT claims

    var authToken = new UsernamePasswordAuthenticationToken(
        username, null, authorities
    );
    // ...
}
```

#### 📝 Улучшения кода:
- Метод `extractJwtFromRequest()` для чистоты логики
- Try-catch для обработки невалидных токенов (логируется в debug)

## 🚀 Производительность

### До рефакторинга:
```
Каждый HTTP-запрос → JwtAuthenticationFilter → UserDetailsService.loadUserByUsername() → SELECT * FROM users WHERE username = ?
```
**Проблема:** N запросов = N DB-вызовов

### После рефакторинга:
```
Каждый HTTP-запрос → JwtAuthenticationFilter → JwtService.extractAuthorities() → Парсинг JWT (CPU-bound)
```
**Результат:** **0 DB-запросов** в hot path

## 🎓 Архитектурное решение

Этот рефакторинг следует best practice **JWT Stateless Authentication**:
- **JWT = Self-contained token** — вся информация о пользователе внутри токена
- **Zero database calls** в hot path → масштабируемость
- **Trade-off:** При изменении ролей в БД нужен logout/relogin (стандартная практика для JWT)

Если требуется **мгновенная отзывка ролей**, рассмотрите:
- Redis-based token blacklist
- Short-lived JWT + Refresh tokens
- Hybrid approach (редкие DB-проверки для критичных endpoints)
